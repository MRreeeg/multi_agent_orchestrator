**三条设计原则（创造模式必须遵守，不要推翻）：**

1. **只加层、不覆盖**：DSH 是分层配置树（bundle → profile → `$DSH_HOME/cordis.patch.yml` → `--patch`），所有自定义都往新层放；`settings.yaml` 只放模型与凭据引用，**永不写 API Key**。
2. **dsh 节点 = run-only**：headless 一次性执行、每次全新会话、无 serve 协议（理由见 §2.1）。不要尝试接入 DSH Web 内部 API 来做 serve。
3. **审批策略硬设为 `never`**：headless 无人应答"允许"，必须用 `DSH_PERMISSION_MODE` 显式映射（§2.3），这是解决"工具允许导致循环卡住"的根治法。

## 2. 关键决策与理由（避免重新决策/踩坑）

### 2.1 为什么只有 run、没有 serve？

Reasonix 的 serve 需要的是**面向程序调用的保留运行时协议**，不是"能跑 Web UI 的服务"：

1. 后端 spawn 常驻进程；
2. 每次节点尝试 = 提交一个 turn、等结果；
3. 能流式收增量（进 Runtime Console）；
4. 能中断当前 turn 但保留会话；
5. 能跨轮复用同一会话。

codex（app-server WebSocket JSON-RPC）、mimo（ACP stdio）、claude（stream-json stdio）都有厂商明确、稳定的程序协议。**DSH 的 Web UI（`dsh web`）不是这种协议**：它是给人用的产品面（Host + 网关 + 前端 + WebSocket 高度耦合、浏览器专属假设、无文档化外部 API），而官方唯一的一次性程序入口 `dsh-headless` 实现是写死的（`sessionId = session-<randomUUID>` 每次全新、任务只走位置参数、结束打印一条文本即退出）。**接入 DSH Web 内部 API 做 serve = 踩 Reasonix 自己"不支持 codex exec-server"的同一类坑**（不能因为都走 HTTP/WS 就假定可互换）。

**通往 serve 的正确路径（建议反馈 DSH 上游，本文件不实现）：**

- 路径 A：DSH headless 增加 `--resume <sessionId>`（launcher 文档已有 `dsh --profile tui --resume <id>` 先例）→ 即可像 `codex exec resume` 一样跨轮续上下文，无需常驻进程。
- 路径 B：DSH 发布 ACP / MCP server profile（仿 `mimo acp`）→ 直接复用 Reasonix 现有 ACP 适配层，serve + 流式 + 中断全套获得。

### 2.2 端口说明（"端口到底是什么"）

端口不是接入机制，serve 缺的是协议。各端口对照：

| 端口 | 是什么 |
|---|---|
| `127.0.0.1:8788` | Reasonix 编排控制台 Web UI（`start.bat` → `/orchestrator`） |
| `127.0.0.1:3080` | DSH Web GUI（本次会话的 `DSH_WEB_URL`） |
| `dsh web --port 8080` | launcher 文档示例，任意可改，无固定语义 |
| `127.0.0.1:<随机>` | codex app-server / mimo acp 等保留运行时的临时 loopback 端口（每次 spawn 动态分配，浏览器不直连） |

DSH web 端口随便改，但改了也变不出 serve 协议——两码事。

### 2.3 审批 / 沙箱映射（"允许"卡循环的元凶）

headless 没有交互审批界面，所以**审批策略必须在启动前用环境变量定死**。DSH 基础组合的规则：

```text
DSH_PERMISSION_MODE == 'danger-full-access'  → 沙箱全开 + 审批 never（自动执行，永不卡）
DSH_PERMISSION_MODE == 'read-only'           → 沙箱只读 + 审批 ask（只读操作不触发审批）
DSH_PERMISSION_MODE == 'workspace-write'     → 工作区沙箱 + 审批 ask（⚠️ headless 无人应答，可能卡住，不要用于编排节点）
```

Reasonix 侧已实现的映射（`dsh_pipeline.go` 的 `dshPermissionMode`）：

| 节点条件 | DSH 环境 |
|---|---|
| `ToolsReadOnly`（dsh 架构师节点自动为 true） | `read-only` |
| `Trust=true` 或 `ApprovalMode=auto/yolo`（编排节点默认） | `danger-full-access` |
| 其他 | `workspace-write`（文档标注不推荐） |

**结论：编排 Loop 里的 dsh 节点默认全自动执行（审批 never），架构师/审查者按角色只读（硬沙箱）。** 这正是"工具允许导致循环卡住"的根治：没有任何人会弹"允许"。

### 2.4 定义式 Agent vs Prompt 式 Harness vs 客制化功能：结论

- **不是二选一，是控制平面不同**：Reasonix = 编排器外部控制（确定、可审计）；DSH 定义式 = agent 内部自治（goal/subagent/workflow 一等公民）；客制化（创作模式）= 定义式之上的一层可编程制品。
- **单看能力上限，DSH 定义式更强**：硬沙箱、审批可硬设为 never、skill 按需加载省 token、工具目录稳定前缀利于 KV cache、Code Mode 一次往返压 N 步、subagent/workflow/ralph 自带。Reasonix 的角色 prompt 是"软约束文本"。
- **正确姿势**：Reasonix 管节点边界 + 审查（确定性），dsh 节点在边界内用定义式能力深挖（自治）。**不要让 dsh 节点把整个 Loop 吞进自己肚子里**（它必须收敛成一条最终文本交回编排器）。
- 详细论证见 `01-对比分析-定义式Agent-vs-Prompt式Harness.zh-CN.md`。

### 2.5 双通道设计（一份 SKILL.md 两套系统消费）

同一个 `<name>/SKILL.md` 同时被两套系统发现：

| 通道 | 发现根 | 效果 |
|---|---|---|
| DSH | `<workspace>/.dsh/skills`、`<workspace>/.agents/skills`、`$DSH_HOME/skills`、`~/.agents/skills` | dsh 节点按 `whenToUse` **按需加载** |
| Reasonix | `~/.codex/skills`、`~/.local/share/mimocode/builtin_skills`、`$REASONIX_SKILL_DIR`/`$REASONIX_SKILLPACK`、`~/.config/reasonix/skills` | 节点 Skill 下拉出现，选中后**注入 prompt**（所有执行器一致） |

skill 文件名（目录名）必须 kebab-case，frontmatter 必须含 `name` + `description`（Reasonix 读 `description:`，DSH 读 `name`/`whenToUse`）。

### 4.3 三个角色 SKILL.md（正文见下，frontmatter 必须保留）

`skills/reasonix-architect/SKILL.md`：

````markdown
---
name: reasonix-architect
description: 架构师节点：只做只读需求分析与技术方案设计，产出模块边界、接口、实施清单与验收标准；绝不写代码、不修改文件、不执行实现命令。
whenToUse: 当节点承担架构师（architect）职责，需要分析需求、设计方案并交给下游执行者时。

# 架构师（Reasonix architect 节点）

## 固定职责（最高优先级）
- 只负责当前这一轮的需求分析、技术方案、模块边界、接口和实施计划。
- 只输出设计方案，不写代码、不修改文件、不执行实现命令，不代替执行者完成任务。
- 不得自行设定一个脱离原始需求的 Goal，不得把原始任务改写成自己的长期目标。
- 不得在节点内部循环、迭代或模拟多轮审查；不得自行执行"第1/2/3轮"，不得等待自己审查通过。
- 输出完成后立即给出最终文本答复并结束；不要声称"执行完后再发送"，因为本节点不执行实现。
- 如果当前流水线启用了 Loop，Loop 由 Orchestrator 在节点外部控制；本次调用只产生当前轮的一份方案。

## 本次调用的输出目标
1. 需求理解与约束  2. 当前轮的技术方案  3. 文件/模块/接口设计
4. 给执行者的明确实施清单  5. 可验证的验收标准

## 能力边界
- 可以读取文件了解项目现状（read / grep / glob / 只读搜索）
- 可以运行只读命令
- 禁止写入、创建、删除文件，禁止执行实现代码

## 输出格式
- 需求理解 / 架构设计 / 接口定义 / 实现步骤 / 给执行者的指令 / 验收标准

## 注意
- 节点的具体职责只能补充当前任务，不能覆盖以上固定边界。
- 一次调用只处理一轮，不自行重复。
````

- 只审查当前这一轮上游节点的输出和工作区结果；**对照架构师设计文档与原始任务判断覆盖度**（不是只看当轮语法）。

- 完成本轮审查后必须立即输出审查结论；下一轮由 Orchestrator 根据 decision 决定。
- 如果启用了 LOOP REVIEW PROTOCOL：只输出协议要求的纯 JSON，不得输出 Markdown，不得调用定时/后台任务。

## 输出目标
- 证据 / 发现的问题 / 修改要求 / pass/revise/blocked 结论

## 审查维度

| 维度 | 检查项 | 严重性标记 |
|------|--------|:----------:|
| **安全** | 路径遍历、命令注入、XSS、SQL注入、鉴权绕过、密钥泄露、反序列化 | 🔴 严重 / 🟡 中 |

| **性能** | 循环低效、内存分配、I/O 阻塞、并发瓶颈、缓存缺失 | 🟡 中 / 🟢 低 |
| **可维护性** | 命名、注释、复杂度、重复代码、模块化、测试覆盖 | 🟢 低 / ⚪ 建议 |

## 输出格式

- 总体评价：pass / revise / blocked

## 能力边界

```text
presets/<id>/
├── agent.cordis.yml      # DSH 定义式组合（Web 交互会话直接选用）
├── preset.yml            # 名称 + 描述（/selfcheck 导入时显示）
└── headless.patch.yml    # headless 扁平化补丁（Reasonix dsh 节点经 --patch 加载）
```

- `install.ps1 -Mode user` 自动装进 `$DSH_HOME/.agent-presets/<id>/`。
- Reasonix 控制台 `/selfcheck` **自动导入**并显示这些预设；dsh 节点配置面板出现「客制化 Agent」下拉。
- 节点选中预设后，执行器用 `--patch <dir>/headless.patch.yml` 跑 headless（persona 覆盖 + 工具裁剪）；预设不存在或无补丁时节点**大声失败**，不静默退回。
- 前端节点卡片明确标注实现方式：`客制化 Agent：xxx`（预设）vs `Prompt 式：内置 persona / Skill 注入`。
- 前端分析师按「管家」标准重写：结论先行、主动体贴、会调度 subagent，不再是"人机"。
- 机制细节与验收见 `04-客制化Agent导入与自检.zh-CN.md`。

> 注意：`headless.patch.yml` 与 `agent.cordis.yml` 的 persona 必须同步维护（前者是后者的 headless 翻译）。

## 5. P1：模型路由细化（可选但推荐）

**事实**：DSH 没有 `--model` 参数；节点 `model` 由执行器翻译成临时 `--patch` 覆盖 `agent-default-model` 组合行（provider=`deepseek-official`）。但 **`$DSH_HOME/settings.yaml` 里保存的 `agent-default-model` 优先于组合层配置**（Web 模型页写的就是它）。

| 方案 | 做法 | 效果 |
|---|---|---|
| A（简单） | 节点填模型 → `--patch` 覆盖 | settings 里有保存值时被忽略 |
| B（严格，推荐） | **每模型一个专用 `DSH_HOME`**，里面只放 `settings.yaml`（key 走环境变量 `DEEPSEEK_API_KEY`） | 节点模型说了算；执行器 `ExecOptions.DshHome` 已支持 |

方案 B 落地（手工版，供创造模式封装成脚本）：

```powershell
# 建两个专用 home
$models = @{ flash = 'deepseek-v4-flash'; pro = 'deepseek-v4-pro' }
foreach ($k in $models.Keys) {
  $home = "G:\dsh-homes\$k"
  New-Item -ItemType Directory -Force -Path $home | Out-Null
  @"
agent-default-model:
  provider: deepseek-official
  model: $($models[$k])
  reasoningEffort: high
"@ | Set-Content (Join-Path $home 'settings.yaml') -Encoding UTF8
  # 注意：headless profile 首次在该 home 下会自动初始化（bundles 从 dsh 安装目录解析，无需重装 node_modules）
}
```

> 控制台侧要"按节点指定 DSH_HOME"，目前 `ExecSpec` 还没有该字段——如需要，在 `internal/orchestrator/types.go` 的 `AgentNode` 加 `dshHome` 字段并在 `dsh_pipeline.go` 透传给 `ExecOptions.DshHome`（执行器已支持，约 10 行改动）。

## 9. 已知限制与规避

| 限制 | 说明 | 规避 |
|---|---|---|
| 任务长度 | 任务走命令行位置参数，Windows ~32K 上限 | 控制节点 prompt 大小；大上下文用 codex/claude serve；根治需 DSH 支持 stdin |
| 无保留会话 | 每次全新会话，`ContextPolicy` 不生效 | 需要跨轮上下文用 codex/claude serve；或等 §7 路径 A |
| 模型路由 | settings 优先于 `--patch` | §5 方案 B（专用 DSH_HOME） |
| 无 usage 回传 | 控制台 token 统计缺失 | 从 `$DSH_HOME\sessions` 会话日志核对 |
| 首次较慢 | headless profile 自动初始化 | 预先预热（§3.4） |
| 审批 ask 会卡 | headless 无人应答 | 必须用 §2.3 映射（默认 danger-full-access / 只读 read-only） |
| dsh 节点自治不可中途插 | 编排器只能等最终文本 | 节点边界收敛；长任务拆成多个 dsh 节点 |
