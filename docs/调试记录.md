## 2026-08-17 审查者维护机制（L-53）

- 背景：便宜的免费模型（opencode 免费 deepseek、免费 mimo-v2.5）在 Loop 执行节点
  上会长时间空转/卡死（"let me explore" 循环、把输出预算烧在复述计划上），轮末
  审查救不了正在跑的执行者。设计稿：
  `docs/superpowers/specs/2026-08-17-reviewer-maintenance-design.md`（已批准）。
- 架构（能力分层，来自代码审计）：
  - T1（serve 模式 mimo/opencode/claude/codex）：有中断+消息通道 → 完整能力
    （nudge = 中断 + 发纠正消息 + 等纠正轮完成）；
  - T2（reasonix serve / run 模式 / dsh）：无 interrupt/message、SSE 只有
    turn_done/ask_request → 只能 restart（杀掉重跑）或 noop，卡住检测退化为
    turn 时长（3min）；
  - T3（run 模式/dsh）：同 T2，restart 为主。
- 触发条件：T1 无进展 90s（轮询 console snapshot 的输出/事件长度变化，2s 间隔）；
  T2/T3 turn 运行超 3min。先中断再诊断（取消执行 → 冻结现场 → 唤醒审查者）。
- 维护者模式（maintenance-plan-v1）：用审查者节点配置（默认 reasonix serve +
  deepseek-flash）独立调用，NeverAsk/MaxSteps=1/executionMode=task/3min 超时，
  与轮末审查互斥（`maintenancePlannerMu.TryLock`，拿不到锁放弃维护走原路径）。
  输出 `{schemaVersion, judgment: nudge|restart|noop, reason, nudge.message |
  restart.correction}`；解析失败给 1 次系统纠正重试，仍失败放弃维护。
- 干预上限：每节点每轮 2 次（stallMaxInterventions）；开关：节点级
  `stallMaintenance`（默认开）+ 全局 env `REASONIX_STALL_MAINTENANCE=off` 总闸。
- 落地文件：
  - `stall.go`（新）：stallWatcher（分档观测）、execWithStallRepair 主循环
    （goroutine 执行 + started 通知 → 按 endpoint 匹配 runtimeID → 卡住 →
    cancel → 现场 → planner → 执行计划）、runStallRepair、waitForTurnOutcome
    （轮询 CanInterrupt→CanSend）、runMaintenancePlanner（含纠正重试）、
    maintenanceEvents 记录 + SSE 广播（PipelineNodeMaintenance 新 kind）；
  - `loop_review.go`：ParseMaintenancePlan / ValidateMaintenancePlan（复用
    scanJSONObjectEnd 最后一个 JSON 扫描策略）；
  - `loop.go`：executeNodeAttempt 改走 execWithStallRepair，restart 产生的新
    attemptID 供外层 UpdateAttempt 记录正确 attempt（含嵌套 restart 时取最深）；
  - `pipeline.go`：executeNodeWithLoopProtocolAtWorkspace 加 variadic
    `startNotify`（onStart 前通知，向后兼容）；Canceled/DeadlineExceeded 分支
    保留部分输出（原实现丢弃，中断现场无从诊断）；
  - `types.go`：AgentNode.StallMaintenance、ExecSpec.StallMaintenance、
    PipelineRun.MaintenanceEvents；
  - 前端 index.html：cfg-stall-maintenance 开关（开启/关闭）、i18n
    cfg.stall/cfg.stallTitle、SSE `pipeline_node_maintenance` 渲染维护干预消息。
- 验证：新增 stall_test.go 11 个用例（开关 env/节点级、解析/校验、快速路径、
  noop 回退、nudge 全流程、restart 新 attempt、planner 失败降级、预算耗尽），
  全部通过；`go build`/`go vet` 干净；node --check（提取内联脚本）通过；
  orchestrator/serve/event 全量测试仅剩预存在的
  `TestRuntimeStatePersistsAndReloads`（干净基线也失败，与本次无关）。
- 坑：
  ① 中断执行者用的 `cancelExec` 会连带杀掉后续维护调用与纠正轮的 ctx——维护
  调用/等待纠正轮必须用外层 run ctx，只有执行者 goroutine 用可取消的 execCtx；
  ② executeNode 在 ctx.Canceled/DeadlineExceeded 时丢弃部分输出，导致中断现场
  无诊断材料——改为返回 result.FinalText（对既有 interrupted 分支无副作用）；
  ③ reasonix（T2）没有 /cancel，SSE 也没有输出增量——T2/T3 只能 restart，
  nudge 分支对 T2/T3 直接跳过并记录事件；
  ④ noop 语义修正：设计稿原写"解除挂起继续等原 turn"，实现时发现 exec 已被
  cancel、无法恢复——noop = 放弃维护，把中断结果交给人工恢复路径（attempt=
  interrupted，部分输出保留）。
- 未提交事项：spec 提交 `2fd2919`/`32e2123` 与 Stage 0-5 改动一并 push。
